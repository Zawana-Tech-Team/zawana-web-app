# Admin court-rental rescheduling

Admin rental moves use a dedicated presentation inside the existing DeskMoveDialog. Weekly-class moves and the FO rental presentation retain their existing layout. The member self-service and private-course rescheduling interfaces remain separate.

The replacement form displays the original court with its recorded/inferred floor, date and time once, followed by New court, New date and Available time. Customer information is retained when available. Native selects support scrolling dialogs without portaled dropdowns closing during scroll. Event/Maintenance reasons remain authoritative. The footer provides Cancel and Review reschedule without a repeated progress strip or instructional header.

Available time now lists only server-verified ranges that fit the original rental duration. The read-only staff endpoint `POST /api/rescheduling/moves/availability` accepts selected booking IDs and each destination court/date, reads calendar data in five parallel queries, and excludes booked/pending reservations, maintenance, weekly blocks, closures, unavailable courts and past starts. It respects recurring-class exclusions and holiday overrides. It ignores only the selected originals so whole-batch swaps remain possible; client selection also excludes conflicts between draft replacements. Final quote and confirmation retain their authoritative validation and locking.

Changing court/date clears the selected time. Live availability refreshes use the existing booking subscription; newly blocked selections are cleared with feedback. Previous-date responses cannot populate the new date. Loading and error states disable the picker and review, with a retry action and no generated fallback slots. An empty successful result explains that another court/date is needed. The member, private-course, weekly-class and FO pickers retain their existing workflows.

Review shows original and replacement schedules side by side on desktop and vertically on phones. It uses the server quote's original snapshot, price basis, destination rate and surcharge. The total additional payment is prominent; payment receipt confirmation appears only when required. Existing cash/verified-online controls, lower-price/no-refund rules, per-rental surcharge calculation, availability checks, revisions, idempotency and audit recording are unchanged. Successful saves use the parent's existing close/refresh behavior. A refresh failure after a successful save cannot expose another confirmation action.

Admin affected-rental requests show one shared customer header when the selected bookings have the same contact, a compact original-booking card and reference per rental, and a required operational reason. Customer notice preview and optional notes use disclosures. No replacement court/date/time input is required or shown. Existing active requests and ineligible bookings are identified without repeated group warnings, and already-sent requests cannot be submitted again. Initial loading, retry and inline send errors preserve meaningful feedback and draft values.

The direct staff reschedule entry has reservation loading/retry feedback, preserves customer identity and avoids repeating the admin modal's title behind it. The FO page keeps its existing title and return control.

Validation: production frontend build, rescheduling lint, the isolated admin rental browser journey and the existing reviewed-rescheduling browser journey. Coverage includes single/group requests, one member notification per group, failure/retry and duplicate submissions, unchanged bookings/ledger after sending, blocked destinations, zero/additional charges, required received-payment confirmation, one surcharge receipt and audit entry, request completion after a move, desktop/tablet/phone layouts, weekly occurrence/series rules, private coach approval and FO history entry points. The new browser journey is included in CI and the stabilization runner.

Availability validation adds service/HTTP tests for duration boundaries, selected-source exclusions, calendar rules, errors, staff authorization and read-only behavior. Its isolated browser journey verifies available-only options, failures/retry, cleared selections, late replies, live conflicts, batch collisions/swaps and 1440/768/390/320px layouts. The availability browser journey is included in CI and the stabilization runner.
