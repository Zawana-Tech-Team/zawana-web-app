# Admin refund dialogs

Admin single-booking and selected-booking refunds use compact booking cards with customer/reference, court and floor, date/time and original paid amount. Processing forms emphasize the refund amount, retain employee/notes and show a returned-payment reference only for online refunds. Original receipts and audit IDs are available in disclosures. Repeated statuses, progress strips and instructional headings are removed. FO dialogs and member refund history retain their existing presentation.

The compact revision narrows single dialogs to 520px and selected-booking dialogs to 660px, removes colored amount panels and nested booking boxes, and reduces section spacing and headings. Amount and method sit together; notes use a short field. The prefilled employee name appears as “Recorded by” with an optional editor, retaining the same required value and audit payload. Single requests combine request reason with receipt details in one disclosure. Selected refunds use flat rows, show the shared payment method before the booking list, and consolidate receipts into one disclosure. Controls retain 44px touch targets. The default mobile form is checked to stay below 700px tall, with the staff editor initially collapsed and usable while typing.

Review preserves the booking context, highlights the amount and method, and retains the confirmation that funds have already been returned. Partial refunds clearly explain the retained balance and closure of the entire reservation. Completed refund details are read-only, show the actual processed time in Yangon and retain staff, notes, returned-payment reference and audit IDs.

Selected refunds still require explicit selection. Blocked or unpaid bookings remain ineligible. Review displays only chosen bookings; each keeps its own refund amount and online reference. Completed entries no longer offer selection or editable fields. Failed entries retain their values and can be corrected and retried independently. Aggregate and per-booking results make partial batch success clear. Switching between form, review and results scrolls the dialog body to the beginning while preserving values; action footers remain visible on phones.

Loading failures offer retry, and processing failures retain draft data. Existing amount limits, real-reference validation, staff authorization, stale-revision checks, duplicate protection, negative refund ledger entries, original-receipt preservation and per-booking transaction boundaries are unchanged. No automatic transfer is introduced. A successful single refund followed by a refresh failure displays the saved record rather than offering another confirmation.

Validation: frontend production build, rescheduling lint, the existing booking-refund and bulk-refund browser journeys, and a new isolated admin refund UI journey. The new journey covers amount limits, mandatory fields, online placeholder rejection, partial refunds, failed processing and retry, duplicate submissions, audited read-only records, explicit batch selection, blocked unpaid entries, mixed success/failure with independent retry, unchanged original receipts and unrelated bookings, and 1440/768/390/320px form/review/result layouts. It is included in CI and the stabilization browser runner.
